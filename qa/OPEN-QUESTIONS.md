# שאלות פתוחות — מערכת QA רב־סוכנית

המסמך מרכז החלטות שלא נכון להמציא בקוד. עד להכרעה, המערכת נשארת עם ברירת־המחדל הבטוחה המצוינת כאן ומדווחת `BLOCKED`, `SKIPPED_BY_CONFIGURATION` או מגבלה מפורשת במקום PASS מלאכותי.

## החלטות חוסמות

| נושא | השאלה שדורשת החלטה | ברירת־המחדל הבטוחה כיום | בעלים/ראיה נדרשים |
|---|---|---|---|
| Platform admin | מהו חשבון ה־Auth/profile המקומי המאושר, אילו פעולות מותרות לו ואיך מוכיחים ששום tenant role אינו נכנס לאזור platform? | התרחיש `platform-admin` נשאר `BLOCKED`. owner אינו תחליף ואינו מקודם. | בעל מוצר + אבטחה + fixture/RLS מאושרים. |
| שער כשירות לשחרור | האם ממצא `medium` מאומת מכשיל release, ואילו observations או flaky results דורשים עצירה? | critical/high וכשל תרחיש מכשילים; `QA_FAIL_ON_MEDIUM=false` עד החלטה מפורשת. | הנדסה + מוצר + אבטחה. |
| סביבת CI | האם CI ירוץ ב־Windows או Linux, ואיך יוקצה stack מבודד לכל job בלי התנגשות ב־`supplyflow-p0`? | אין workflow אוטומטי; הרצף מתועד בלבד והרצה אחת בכל פעם. | DevOps עם proof של Docker/Supabase/PowerShell/Chromium. |
| מדיניות AI | איזה provider/model מאושרים, מהי מדיניות retention/region, מה התקציב ומי רשאי להפעיל network call? | `QA_AGENT_ENABLED=false`; ללא provider/model/key מאושרים השלב דולג, או `BLOCKED` אם הופעל במפורש. | אבטחה, פרטיות ובעל תקציב. |
| חשבונאות | מהן תוצאות האמת לכל תרחיש כספי: סכומים, עיגול, הקצאות N:M, מעברי סטטוס, retry/idempotency וסיבת audit? | verifiers בודקים רק חוזים שכבר אושרו; אי־בהירות מדווחת כמגבלה. | חשבונאי/ת ובעל מוצר; עדכון `docs/OPEN-DECISIONS.md` כשנדרש. |
| Retry תשלום דרך UI | האם בקשת תשלום שבוצעה צריכה להישאר ניתנת לניסיון חוזר מבוקר, ובאיזה מזהה idempotency? | ההעברה הראשונה מאומתת; לאחר הצלחה השורה עוברת להיסטוריה ללא פעולה ולכן כיסוי retry נשאר `BLOCKED`. | בעל מוצר + כספים + חוזה UI/API מאושר. |
| סיבת ייבוא בנק | מהו השם הנגיש והמחייב של שדה הסיבה לפני התאמה, והאם הוא תנאי audit? | הבדיקה אינה מנחשת locator מבני; תרחיש ההתאמה נשאר `BLOCKED` עד לשם נגיש וחוזה מאושר. | בעל מוצר + נגישות + כספים. |

## החלטות תפעוליות

| נושא | שאלה | מצב נוכחי |
|---|---|---|
| שמירת artifacts | כמה זמן שומרים HTML/JSON/screenshots/traces, מי רשאי לגשת ומתי מוחקים? | `qa:full` שומר `.qa-runs/<runId>/`; auth state וסיסמאות נמחקים. אין SLA retention. |
| סיווג מידע | האם screenshots, URLs ושמות ישויות דורשים סיווג או DLP נוסף לפני העלאה ל־CI? | redaction ומסכות מופעלים, אך כל artifact נחשב פנימי ודורש בדיקה לפני שיתוף. |
| מדיניות flaky | כמה ניסיונות ובאיזה חלון הופכים תוצאה ל־flaky מאומת, ומתי מותר quarantine? | Playwright מבצע retry אחד; הדוח מסמן reproducibility, ללא quarantine שקט. |
| כיסוי דפדפנים | האם נדרש Firefox/WebKit, גרסאות Chrome נוספות או שילוב OS? | Chromium בלבד. |
| מטריצת מכשירים | אילו מכשירי מטבח, רזולוציות, touch/keyboard ותנאי תאורה הם תנאי קבלה? | בדיקה אוטומטית אחת ב־390×844; מכשיר אמיתי נשאר בדיקה אנושית. |
| רשת והתאוששות | מהם latency, packet loss ו־offline windows מייצגים, ומהי התוצאה הרצויה אחרי retry? | אין network shaping אוטומטי; בדיקה אנושית נדרשת. |
| ביצועים | מהם ספי זמן, נפח נתונים ומספר מסמכים/ספקים מייצגים? | אין load/performance gate; fixtures קטנים וסינתטיים. |
| cleanup כושל | מי מטפל ב־state שנשאר כאשר reset או מחיקה נחסמו, ומה חלון התחזוקה המותר? | אין force cleanup. עוצרים תהליך מתחרה ומריצים `qa:clean` שוב. |
| עלות AI | מהן מגבלות token, זמן ו־concurrency לריצה מלאה? | 30 צעדים ושני retries לכל תפקיד כברירת מחדל; אין SLA עלות. |
| עדכון prompts | מי מאשר שינוי prompt שמשנה התנהגות תפקיד או עדיפות תרחיש? | שינוי prompt דורש review כמו שינוי בדיקה; הוא אינו משנה הרשאות או חוזה עסקי. |

## קבלה אנושית שטרם הוגדרה במלואה

1. מי בודק screen reader בעברית, ובאילו צירופים של קורא מסך, דפדפן ו־Windows/mobile?
2. מי חותם על נכונות הדוחות וה־exports עבור הנהלת חשבונות?
3. מי מייצג עובד מטבח ובאיזה מכשיר אמיתי מתבצעת בדיקת קבלת סחורה?
4. מי מייצג ספק ובודק שהמחירון החודשי ברור ללא הדרכה?
5. אילו תרחישי רשת איטית, ניתוק וחזרה נחשבים תנאי קבלה?
6. אילו פעולות כספיות דורשות בדיקת four-eyes אנושית גם כאשר verifier עבר?

## תנאים לפתיחת תרחיש Platform Admin

אין לשנות את `platform-admin` מ־`BLOCKED` ל־`READY` לפני שכל התנאים הבאים מתקיימים:

- fixture Auth/profile מקומי נפרד ומאושר, שאינו אחד מששת חשבונות הדייר;
- חוזה תפקיד ומסלולים מתועד במוצר ובארכיטקטורה;
- בדיקות server-side שמוכיחות שכל tenant role חסום;
- בדיקת audit לפעולות platform רגישות;
- מחיקה מלאה של החשבון וה־state ב־cleanup;
- אישור מפורש של אבטחה ובעל המוצר.

## מה אינו שאלה פתוחה

- סביבת הבדיקה נשארת local-only מול `supplyflow-p0` ו־`127.0.0.1:55431`.
- `service_role` אינו נשלח לדפדפן, למודל, ל־storage state או לדוח.
- אין ליצור PASS על ידי תיקון נתוני production, קידום owner או עקיפת RLS.
- Axe אינו תחליף לבדיקת WCAG אנושית.
- חסרון מפתח AI אינו חוסם שלב דטרמיניסטי כאשר `QA_AGENT_ENABLED=false`; הוא חוסם רק את שלב הסוכנים כאשר הופעל במפורש.
- `BLOCKED` ו־`SKIPPED_BY_CONFIGURATION` אינם שקולים ל־`PASSED`.
