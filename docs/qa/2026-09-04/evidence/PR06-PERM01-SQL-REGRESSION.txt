PR06 - PERM-01 - REGRESSION - what else a REVOKE could have taken with it
========================================================================
Local stack at head 0319 (0310 0311 0312 0313 0314 0315 0319), 05.09.2026, immediately after the
GREEN run and before `npm run demo:restore`. Exclusive hold of the campaign's Supabase lock.

WHY THIS FILE EXISTS. A `REVOKE` is the one change in this campaign that can break every open tab
in the product: the client asks for a column it may no longer have and PostgREST refuses the WHOLE
statement with a 403, nowhere near the line that caused it. A green oracle on its own would only
say the leak closed. These seven say nothing else lost a read it needs.

Each suite was run ON ITS OWN -- one docker cp, one docker exec, its own captured output -- against
the same database, in the order below. All seven end in `rollback`, so none of them left state for
the next.

  docker cp  supabase/tests/<suite>.sql supabase_db_supplyflow-p0:/var/lib/postgresql/reg-<n>.sql
  docker exec -e PGPASSWORD=postgres -e PGTZ=Asia/Jerusalem supabase_db_supplyflow-p0 \
    psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f /var/lib/postgresql/reg-<n>.sql

THE TWO THAT COULD HAVE BROKEN, AND DID NOT
  p1_financial_commands carries the all-tables ACL contract this migration was written around: for
  every table in `public`, a permissive read policy exists if and only if `authenticated` can read
  it. 0319 revokes the TABLE grant on profiles and organizations and re-issues it column by column,
  which is exactly the 0112 shape that contract already allows ("COLUMN-level SELECT counts"), and
  it narrows the two configuration tables in the POLICY while KEEPING their grant. Both halves are
  proved here rather than argued: the suite passes.

  p0_client_dml_acl is the suite that executes refusals rather than reading the catalogue. It
  passes unchanged, which also says the 42501 the oracle now relies on is the ordinary column ACL
  denial this image raises cleanly.

p22_trial_read_only -- PRE-EXISTING, NOT CAUSED BY THIS CHANGE, AND SAID WITH ITS OWN WORDS
  It fails at its own line 81:

    update public.organizations set status = 'trial', trial_ends_at = ...
    ERROR:  trial_retired
    CONTEXT:  PL/pgSQL function private.organizations_trial_write_guard() line 12 at RAISE

  Three independent reasons this is not 0319's doing, none of which needs a second reset to check:

  1. The guard is unconditional. `private.organizations_trial_write_guard`, as it stands in the
     database, opens with

       if new.status = 'trial' or new.trial_ends_at is not null then
         raise exception 'trial_retired' using errcode = '22023';

     Every write p22 makes to set up its fixtures matches that. The suite cannot pass at ANY head
     from 0134 onward, with or without 0319. The guard was retired into this shape by 0134, 185
     migrations before ours.
  2. It is a trigger RAISE, not a privilege error. 0319 changes SELECT privileges and two read
     policies; it grants and revokes nothing on writes, and anchor (b) of the migration plus the
     `catalogue/self-service-update-kept` control both assert the UPDATE privileges are intact.
  3. The failing statements run as the `postgres` superuser -- the suite has not switched role at
     that point -- and column privileges do not apply to a superuser at all.

  It is also not in CI. The suite is absent from `scripts/check-quality-gates.ps1`, and its own
  header says why, in its author's words: "RETIRED, AND KEPT ON PURPOSE ... It is NOT in the 118
  suites `scripts/ci-sql-suites.mjs` runs, it would fail if it were, and it must not be re-wired."
  It was run here anyway because the task named it; the result is recorded rather than waved at,
  and nothing was changed to make it pass. Re-wiring it would be re-opening a retired decision
  (OPEN-DECISIONS #15), which is not this PR's business.

  This matters because a function-EXECUTE denial takes this image's backend down; every privilege
  question about a FUNCTION in this repository is answered from `has_function_privilege` for that
  reason. The refusals this campaign step executes are table/column ACL denials, which raise 42501
  cleanly -- and the count says so.
