THE CONCURRENCY PROOF IS A MEASUREMENT, NOT AN ARGUMENT
--------------------------------------------------------
p115 runs the race through two independent `dblink` sessions: session A inserts 2,000.00 and then
SLEEPS 1.2s INSIDE ITS TRANSACTION — after the guard has taken the line's row lock, before it
commits — and session B is dispatched 0.2s later, so B is measurably behind rather than merely
second in the file. p115 asserts the shape and passed; but it drops its own schema on success, so
the per-session messages cannot be read out of it afterwards. They were therefore reproduced
verbatim by a supplementary probe on the SAME guarded database immediately after the green run,
racing 2,000.00 + 2,000.00 at a fresh 2,950.00 line:

    === the two sessions, verbatim ===
      session  |                 result
    -----------+----------------------------------------
     session_a | ok
     session_b | bank_allocation_exceeds_statement_line
    (2 rows)

    === what the 2,950.00 line ended up holding ===
        reference    | line_amount | currency | confirmed_claimed | confirmed_rows
    -----------------+-------------+----------+-------------------+----------------
     P115-PROBE-OVER |    2950.000 | ILS      |          2000.000 |              1
    (1 row)

Session B did not fail on a deadlock, a serialisation error or a timeout — it blocked on the row
lock the guard takes over the affected statement lines in id order, and when session A committed it
re-read under a fresh statement snapshot that contained A's row and was refused BY THE PROJECT'S OWN
NAMED ERROR. On the unfixed tree the identical race left 4,000.00 on that 2,950.00 line.

The probe is supplementary and is not a suite; it lives only in this evidence file. It was run on
the guarded database and its row was removed by the following reset.

WHAT WAS PROVED ON THE GUARDED PATH, AND WHAT ON THE PRIVILEGED ONE
---------------------------------------------------------------------
`command_second_full_match` and `suggestion_beside_a_full_line` run as role `authenticated` with a
real `request.jwt.claim.sub`, calling `public.match_bank_transaction` — RLS, `auth_role()` and
`p1_financial_command_guard` all in front of the write. The refusal reaches an end user by name
through the product's own door.

The TABLE arm writes `public.bank_allocations` directly and cannot do otherwise: `0023:166` revokes
insert, update and delete on this table from `authenticated`, so every product write to it already
happens inside a SECURITY DEFINER function at the definer owner's privilege. A direct write here is
not a way around the guard — it is the exact level at which every real write runs, and the only way
to reach two of the oracle's three cases at all, since no command moves an allocation between lines
and `match_bank_transaction` locks the line before this guard can ever see two commands at once.

RESIDUAL, RECORDED RATHER THAN SILENTLY FIXED
-----------------------------------------------
`match_bank_transaction` never clears the suggestions on a line it confirms, so every confirmed
match leaves its suggestion beside it. That is the "two rows of 2,950.00" appearance the finding
reported. Correcting it would delete financial rows and decide which row is real, so it stays the
owner's decision; DEBT §122 carries the reason. The existing production pair on line
`fa000000-…-0008` was not touched.
