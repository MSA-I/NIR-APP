HOW THESE WERE RENDERED, AND WHAT THAT DOES AND DOES NOT PROVE.
The shared local Supabase stack is held by another agent this wave, so nothing here was rendered
against a database. `PaymentRequestDetail` was mounted in jsdom against hand-written fixtures — the
same MSW fixtures the oracle uses — and the markup it produced was written to .tmp and served to a
real browser together with the product's OWN built stylesheet (`vite build` into .tmp/dist, the
Tailwind v4 output from `src/index.css`). So the colours, the disabled state, the RTL layout and the
type are the product's; the DATA is fixture data. These images prove WHAT THE COMPONENT DRAWS for a
given server answer. They do not prove what the server answers — that is `p1_transition_payment_request`
and it is untouched by this PR.
No git state was changed to produce them. The harness spec that emitted the markup lived in the tree
for the length of the run and was deleted; `.tmp/` is gitignored.
NOT rendered: the live tenant, the list screen behind the modal, and 390px — REQ-01 is not a mobile
finding and the panel it names is this modal.

The approval stays open and stays the primary action. This is the half a fix like this gets wrong:
closing a button is only correct where the server refuses ABSOLUTELY, and `review_status <> 'approved'`
is the one arm on this panel that does. A warning is still a warning.

WHY NO THIRD IMAGE FOR THE "already paid" CRITICAL. `invoice_paid_*` fires on `balance <= 0`
(`0219:342`), and an allocation above that same balance is exactly what `over_allocated_invoice_count`
counts, with the identical expression (`0219:409-423`) the approval barrier uses. So a paid invoice
carrying a positive allocation always arrives with `over_allocated_invoice_count >= 1` and is already
closed by `overAllocated` (0146). A fixture with `paid_invoice_count: 1` and
`over_allocated_invoice_count: 0` is a combination the server cannot produce, and rendering one would
have been a picture of a state that does not exist.
