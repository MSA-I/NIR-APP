PART 0 — THE FINDING'S OWN DIAGNOSIS IS WRONG, MEASURED
-------------------------------------------------------
FIN-04 says: "a phantom '$ 0' balance row on a supplier with NO DOLLAR ACTIVITY".
MON-03 says that reading is INVERTED. MON-03 is right. Measured read-only against the
production project (rkftlbctohswhbbiaqin) through scripts/db-query.ps1, 2026-09-05, on the
very supplier the sweep photographed (aa000000-0000-4000-8000-000000000013):

  currency  review_status  invoices  total     paid      open_balance
  ILS       approved       1         900.000   750.000   150.000
  USD       received       1         300.000   0         300.000

The supplier owes 300 dollars. The dollar invoice is `received`, not `approved`. So the
accountant's `$ 0` is not a phantom row over an empty currency — it is a FALSE STATEMENT OF
SETTLEMENT printed over a real debt, to the one person whose job is to reconcile against a bank
statement. The sweep's own screenshot (out/finance/20-finsup-0013.png) shows exactly the two
lines this table predicts: 150 ILS, and $ 0 where 300 stands.

PART 3 — THE FIX
-----------------
supabase/migrations/0320_a_currency_this_role_cannot_value.sql — ONE anchored DO block, TWO
anchors on one definition, each with its occurrence count asserted = 1, executed once:

  (1)  `  left join balances b on b.invoice_id = i.id`
    -> `  join balances b on b.invoice_id = i.id`
  (2)  `         coalesce(sum(b.balance_in_currency), 0)::numeric(14,3),`
    -> `         sum(b.balance_in_currency)::numeric(14,3),`

Every row the function emits is now one the caller's OWN read valued. A currency this role
cannot value emits no row, which is the same answer 0218 already gave for a supplier with no
invoices, and components/Money.tsx:67 already draws that as an em dash. Anchor (2) is removed
rather than left dead because it is half of the named mechanism.

A5: private.scope_definer_enforcements is re-pinned from pg_proc with a new scope_proof; the
hash is COMPUTED, never written as a literal.

DRY RUN OF THE PATCH, no database involved: the two anchors were parsed back OUT of the
migration file and applied to the live body captured in PART 2.

  anchor 1 occurrences in the live body: 1  OK
  anchor 2 occurrences in the live body: 1  OK
  resulting body:
      select s.id,
             i.currency,
             sum(b.balance_in_currency)::numeric(14,3),
             count(b.invoice_id) filter (where b.balance_in_currency > 0)
      from public.suppliers s
      join public.invoices i
        on i.org_id = s.org_id and i.supplier_id = s.id and i.deleted_at is null
       and i.financial_role = 'payable'
       and (i.unit_id is null or i.unit_id = any(public.auth_scopes()))
      join balances b on b.invoice_id = i.id
      where s.org_id = auth_org() and auth_role() in ('owner', 'accountant')
      group by s.id, i.currency
  the migration's own sentinels, checked against that result:
      has sum(b.balance_in_currency)::numeric(14,3) : true
      has left join balances                        : false
      has coalesce(sum(b.balance_in_currency)       : false
      and the positive sentinel is ABSENT from the ORIGINAL body : true

That last line is the one that matters: the sentinel is a property the patch CREATES, so the
assertion cannot pass on a body that was never patched. `coalesce(sum(b.balance_in_currency),
0)::numeric(14,3)` does not contain `sum(b.balance_in_currency)::numeric` — the `, 0)` sits
between — which is why testing only for the ABSENCE of the old shape would have been worthless.

`i.currency` is deliberately NOT rewritten to `b.currency`. After an inner join the two are the
same value by construction (the invoice reader selects `i.currency` for the same invoice), so
the change would be two more anchors for no behaviour at all.

THE OWNER'S FIGURES CANNOT MOVE, and this is structural rather than hopeful: the four
predicates the supplier reader puts on public.invoices (same org, deleted_at is null,
financial_role = 'payable', null-or-auth_scopes unit) are exactly the four the invoice reader
applies, and the owner's arm adds nothing else — so for an owner every joined invoice already
had a balance row and INNER drops nothing. p113 proves it on the guarded path anyway.

PART 5 — SQL SUITE p113
------------------------
supabase/tests/p113_a_currency_this_role_cannot_value.sql, registered in
scripts/check-quality-gates.ps1 as the LAST SQL suite, immediately after p108 (default role
postgres; the whole file is one transaction ending in rollback, so it commits no fixture and no
reset step is added). Appended rather than filed beside its per-currency relatives p80-p93 on
purpose: inserting mid-sequence renumbers every later ordinal and turns a one-suite addition
into a 129-line baseline diff, which is exactly the noise that trains reviewers to skip the
file check:baseline-drift asks them to read. Appended, the baseline diff is the one added
entry. Order is otherwise free here — the suite commits nothing, so no later suite can observe
that it ran.

Fixture, a faithful copy of the production row measured in PART 0:
  A  ILS 150 approved   +  USD 300 NOT approved     <- the MON-03 supplier
  B  ILS 640 approved   +  USD 200 approved         <- control: a currency the role CAN value
  C  ILS 400 approved, paid 400 -> balance 0.000    <- control: a MEASURED zero stays a zero
  D  USD 500 NOT approved only                      <- FIN-04 as a whole card

Every reading is taken with `set local role authenticated` and a real request.jwt.claim.sub, as
the owner and then as the accountant, through the VIEW the client reads — so RLS, the view
grant, security_invoker and the role arms are all in the path. A reading taken as postgres would
prove nothing. The fixtures are written with no end-user subject on purpose: that is what
p1_financial_command_guard lets through, and the approvals still go through
set_invoice_review_status as an authenticated owner because 0099 forbids materialising an
approved invoice any other way.

Assertions are PER ROW, never by count: each (supplier, currency) is looked up on its own AND
the whole row set is enumerated as one string carrying every amount and every open-invoice
count. Expected:
