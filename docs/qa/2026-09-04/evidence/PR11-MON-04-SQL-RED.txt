WHAT WAS REVERTED TO PRODUCE THE RED, AND WHY IT IS ONE OBJECT RATHER THAN A MIGRATION
--------------------------------------------------------------------------------------
Migration 0322 was APPLIED IN FULL and then exactly one object was dropped:

    drop trigger bank_allocations_statement_line_guard on public.bank_allocations;

Nothing else changed. The function `public.guard_bank_allocation_within_statement_line()` and the
index `ba_transaction_idx` stayed in place; the migration set was not touched; the suite file was
not touched. Holding 0322 back entirely would also have removed the index and the function, so a
failure could have been read as "the migration is missing" rather than "the bound is missing".
Dropping the trigger alone makes the red say one thing: the invariant is unasserted.

The suite file is byte-identical in both runs. SHA-256 read back INSIDE the container both times:

WHAT THE RED DOES NOT CLAIM
----------------------------
The finding's wording — "two CONFIRMED allocations of 2,950.00 each" — is not what production
holds; see PR11-MON-04-PRODUCTION-MEASUREMENT.txt. Zero lines anywhere have confirmed allocations
exceeding the line. The defect proved above is the larger one the oracle names: `bank_allocations`
has carried no bound of any kind since `0001`.
