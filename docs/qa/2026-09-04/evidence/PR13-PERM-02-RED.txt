WHAT MAKES THIS A RED AND NOT A HAND-WRITTEN REVERT

holders_own_record.sql` was MOVED OUT of the migrations directory entirely and the database

THE HARNESS WAS CORRECTED BEFORE EITHER SIDE WAS RUN — AND BOTH SIDES RAN AGAINST THE
CORRECTED FILE
-------------------------------------------------------------------------------------

failing assertion, so it did NOT have the structural defect PR 5+6 found in p112. It had a
smaller one: the verdict block names only the pairs that DISAGREED, so on a red run the
pairs that agreed are invisible and "the controls were green" would have been an inference
drawn from an absence rather than a thing anyone read.

One additive change was made: a roll-call, raised as a NOTICE inside the same `$report$`
block before the verdict, printing EVERY expected/observed pair with its own PASS/FAIL and a
[control] marker, plus a tally. No assertion, expectation or fixture was altered — the
change can only add output. RED and GREEN were then both run against this corrected file,
and its SHA-256 was read back INSIDE the container on both sides and is identical.

WHAT THE RED SAYS, READ RATHER THAN COUNTED
-------------------------------------------------------------------------------------
22 of 25 pairs pass and 17 of 17 CONTROLS PASS IN THE SAME RUN, so this is a red about the
policy and not a red about a broken harness — a harness that was not measuring RLS would
have shown the controls failing beside the finding, in this same list.

The three failures are the finding and nothing else:

  * accountant_a reads pw_owner_a  — the owner's password change. They are not its subject.
  * accountant_a reads pw_office_a — a colleague's. They are not its subject.
  * accountant_b reads pw_owner_b  — the same leak, proved a second time in a second tenant,
    so it is a rule of the policy and not an accident of one fixture.

Asserted PER ROW, PER ACTOR. A count would have agreed for the wrong reason: "the accountant
reads 2 rows" is equally true of an accountant reading two rows they are the subject of
neither of, and of one reading their own row plus a colleague's.

Note which lines already pass in the RED and must therefore still pass in the GREEN — they
are regression guards, not things 0323 has to create:
  * accountant_a / pw_accountant_a — the subject reads their OWN record.
  * owner_a on every password row of its tenant — the audit surface.
  * office_a on all four rows — office reads no audit row at all, not even its own.
  * every cross-tenant pair.
A fix that "closed" the finding by breaking any of those would be a narrowing that broke the
screen it was meant to protect, and would show up here as a green that lost a passing line.
