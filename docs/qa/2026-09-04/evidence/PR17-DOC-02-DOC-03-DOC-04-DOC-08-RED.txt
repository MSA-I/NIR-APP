local stack rebuilt from scratch with `npx supabase db reset` from this worktree. The head was
then READ, not assumed — another campaign on this machine has rebuilt this shared database twice

THE ORACLE WAS CORRECTED THREE TIMES BEFORE THIS RUN, AND BOTH SIDES WERE THEN RUN AGAINST THE
CORRECTED FILE. Stated here rather than left for a reader to notice a hash change:
  1. The fixture INSERTed an `org_autonomy_policies` row for `document.interpretation`. Every
     organisation is BORN with one, so it died on `org_autonomy_policies_org_key` before a single
     case was recorded. It is an upsert now.
  2. The fixture wrote `document_interpretations.suggested_supplier_id`. That column is GENERATED
     from `payload -> 'supplier' ->> 'suggested_id'` and the database refuses a non-default value
     for it. The suggestion now reaches the ladder the only way it ever does — through the payload.
  3. `p111_seed` inherited whatever JWT subject the previous case had read as, so the first seed
     for the SECOND tenant was a JWT-authored write for another organisation and `audit_row_change`
     refused it by name (`audit_source_org_mismatch: documents`). The seed clears the JWT itself
     now, because forgetting it once at a call site is silent until it is not.
  Five EXPECTATIONS were also wrong and were corrected against what the unfixed tree actually
  returns, never the other way round: `price_baseline_unknown` is a pre-existing WARNING (0105)
  that fires on every mapped line for which this tenant holds no contracted price. It is now
  NAMED in the expected string rather than filtered out, so those cases state the line's complete
  verdict and a new finding appearing there would fail them.

WHAT THE RED SHOWS, and it is the finding rather than a harness fault — the ten controls prove
that in the same run:

  * `shekel-word/unit-price-line-{0,1,2}` — all three read `(null)`. The payload prints
    `4.20 ש"ח`, `50.00 ש"ח`, `12.90 ש"ח`, exactly as production does. This is DOC-08: the review
    grid's `מחיר במסמך` column IS `lines[].unit_price`, and it is empty on every line.
  * `shekel-word/lines-net` — `0.00`. A MEASURED zero over three lines that were all skipped.
  * `shekel-word/lines-vs-header-gap` — `-969.00`, a subtraction performed against that zero.
  * `shekel-word/missing-rungs` — `[]` and it PASSES in the red, which is the point: the ladder
    whose only job is to name the number it could not read reported that none was missing while
    `lines_net` was a fiction. It is the one case whose observed value is right for the wrong
    reason before the fix, and it stays `[]` after, because after the fix the sum is real.
  * `shekel-word/no-header-mismatch-finding` — `present`. The document is blocked with
    `header_total_differs_from_lines` on a comparison against a number nobody measured. That is
    DOC-03 verbatim.
  * `shekel-word/state` — `blocked`, `approval_blocked` `true`, on a document whose lines sum to
    exactly its header. That is DOC-04: read accurately, and no business record.
  * `price-absent/*` — the general defect that SURVIVES the parser fix. One of two lines has no
    printed price, and the sum published `20.00` — a partial sum presented as the document's,
    with `lines_counted` absent, `lines_net` not in `missing_rungs`, no finding naming the missing
    price, and a header block on the difference.
  * `other-currency/*` — `$12.50` on an ILS document falls silent: same `(null)` as a price that
    was never printed, and no reason recorded anywhere.
  * `filing/date-unreadable-names-the-date` and `filing/number-unreadable-names-the-number` — both
    observe `invoice_identity_missing`. One code, one sentence, two obstacles. On production that
    sentence told a reader the invoice number was missing while the screen displayed
    `SI266001312` at confidence 0.95.

THE TEN CONTROLS, ALL GREEN HERE AND ALL GREEN IN THE GREEN RUN:
  * `control/plain-price-still-reads` (3.50) and `control/comma-line-total-still-reads`
    (1,890.00 -> 1890.00). The entire risk of swapping a money parser lives in these two.
  * `control/header-mismatch-still-blocks` — a document whose lines really DO disagree with its
    header still raises `header_total_differs_from_lines`. 0324 gates that comparison on coverage;
    it must not have deleted it.
  * `control/quantity-unreadable-still-fires`, `control/product-unidentified-still-fires`.
  * `control/cross-tenant-read-refused` — `document_not_found`. A red here would mean the harness
    lost its tenant and nothing else in the run is evidence.
  * `control/filing-both-missing-unchanged` — `invoice_identity_missing` survives for the one
    state it always described correctly.
  * The three `structure/*` rows, including the two that state what may NOT execute: the private
    readers hold no EXECUTE for `authenticated` or `anon`, and the apply command grants
    `service_role` and not `authenticated`. Every EXECUTE question in this suite is answered from
    `has_function_privilege`, never by calling — that denial segfaults this Postgres image.

THE GUARDED PATH, AND IT IS TWO. Sections 1-3 read through `public.get_document_review_assessment`
as role `authenticated` with a real JWT subject, so `auth.uid()`, `auth_org()`, `auth_role()` and
`auth_scopes()` are all in the path; `private.document_reconciliation_assessment` holds no EXECUTE
for any client role and is never called directly. Section 5 reaches the filing ladder through
`public.apply_document_interpretation` with no JWT — the trusted shape the Edge Function uses —
because that command grants EXECUTE to `service_role` and NOT to `authenticated`, so calling it as
a browser role would have measured the missing grant and never the ladder.
