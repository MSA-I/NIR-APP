PR 14 — MON-03 / FIN-04 / FIN-07 — WHAT THE FOUR SCREENSHOTS ACTUALLY SHOW
=========================================================================

Every image below was OPENED AND LOOKED AT, not inferred from the DOM dump beside it. Where the two
disagree that is said. The machine-written companions are `PR14-RED-screen-read.txt` and
`PR14-GREEN-screen-read.txt`, which record the text the page returned; this file records the
picture.

Capture conditions, identical for all four: headed system Edge via `executablePath` (Playwright's
bundled chromium fails `spawn UNKNOWN` on this machine), viewport 1440x900, `reducedMotion:
'reduce'`, `locale: 'he-IL'`, `serviceWorkers: 'block'`, real sign-in as the demo accountant through
`/login` against the local stack. Camera: `scripts/pr14-supplier-currency-visual-check.cjs`.

The RED pair was taken on the database WITHOUT `0320` and with the pre-fix wording of the two
`FIN-07` labels temporarily restored, so the "before" is what a reader actually met. The GREEN pair
was taken after `supabase db reset` WITH `0320`, on the restored tree.

`/finance/suppliers/aa000000-0000-4000-8000-000000000013`, signed in as the demo accountant.

A row of four KPI cards runs right to left across the top. The rightmost, "יתרה פתוחה", is the one

Both in the same weight and size. Nothing on the card distinguishes the first line — a figure this

The three cards to its left read "חשיפה שהגיעה למועד — " (an em dash, correctly, for a metric with

Directly UNDER that `0 $`, in the blue information banner: "אין במערכת מועדי פירעון שמאפשרים לחשב
חשיפה שהגיעה למועד; לכן מוצג — ולא אפס." — the product stating its own policy, that a metric with no
data is drawn as an em dash and never as a zero, immediately below a zero that breaks it.

Below that, the feed "חשבוניות זמינות לתפקיד" lists exactly two rows: `MON03-ILS` 150 ₪ marked
"לא שולמה", and `3377` 0 ₪ marked "שולמה". BOTH ARE SHEKEL INVOICES. The USD 300 invoice that the
`0 $` is a statement about is not on this screen at all — the accountant cannot see the debt and
cannot see any hint that a debt exists. That is what makes the zero a false statement of settlement
rather than a cosmetic extra line: there is nothing on the page to contradict it.

APPENDIX — THE SCREENSHOT FIXTURE, VERBATIM, SO THE FOUR IMAGES CAN BE REPRODUCED
--------------------------------------------------------------------------------------------

`supabase/demo/demo_seed.sql` carries no dollar invoice at all, so the shape production has — and
that the sweep photographed — does not exist locally. It was reproduced with the SQL below, run as
`postgres` against the demo tenant after `npm run demo:restore` and BEFORE each pair of shots. It is
kept here rather than added to the repository because it is a one-off camera prop, not a suite: it
belongs to these four images and to nothing else.

The shekel invoice is approved through `public.set_invoice_review_status` with role `authenticated`
and a real subject — 0099 forbids a fixture from materialising `approved` any other way. The dollar
invoice is left at `received` on purpose: that is the state the accountant's arm of
`p0_invoice_balance_rows_by_currency()` stops at, and therefore the state that produced the `$ 0`.

    begin;
    delete from public.invoices where id in (
      'f4000000-0000-4000-8000-0000000000a1', 'f4000000-0000-4000-8000-0000000000a2');
    insert into public.invoices (
      id, org_id, unit_id, supplier_id, invoice_number, invoice_date, received_date, received_by,
      amount_before_vat, vat_amount, total_amount, review_status, payment_status, currency)
    select v.id::uuid,
           '11111111-1111-4111-8111-111111111111'::uuid,
           (select u.id from public.org_units u
             where u.org_id = '11111111-1111-4111-8111-111111111111'
               and u.unit_type = 'legal_entity' order by u.created_at, u.id limit 1),
           'aa000000-0000-4000-8000-000000000013'::uuid,
           v.number, current_date, current_date,
           (select p.id from public.profiles p
             where p.org_id = '11111111-1111-4111-8111-111111111111' and p.role = 'office'
             order by p.id limit 1),
           v.amount::numeric, 0, v.amount::numeric, 'received', 'unpaid', v.currency
    from (values
      ('f4000000-0000-4000-8000-0000000000a1', 'MON03-ILS', '150', 'ILS'),
      ('f4000000-0000-4000-8000-0000000000a2', 'MON03-USD', '300', 'USD')
    ) v(id, number, amount, currency);

    -- only the shekel invoice is approved, and it is approved the way production approves one
    select set_config('request.jwt.claim.sub', (select p.id::text from public.profiles p
      where p.org_id = '11111111-1111-4111-8111-111111111111' and p.role = 'owner'
      order by p.id limit 1), true);
    select set_config('request.jwt.claim.role', 'authenticated', true);
    select set_config('request.jwt.claims', jsonb_build_object(
      'sub', (select p.id::text from public.profiles p
               where p.org_id = '11111111-1111-4111-8111-111111111111' and p.role = 'owner'
               order by p.id limit 1),
      'amr', jsonb_build_array(jsonb_build_object(
        'method', 'password', 'timestamp', extract(epoch from clock_timestamp())::bigint))
    )::text, true);
    set local role authenticated;
    select public.set_invoice_review_status(
      'f4000000-0000-4000-8000-0000000000a1', 'in_review', 'MON-03 screenshot fixture');
    select public.set_invoice_review_status(
      'f4000000-0000-4000-8000-0000000000a1', 'approved', 'MON-03 screenshot fixture');
    reset role;
    commit;

AND ITS RETIREMENT, run before the stack was handed back, so the next agent's demo tenant does not
inherit two invoices this one invented. SOFT, because financial rows are soft-deleted only — and
because the database enforced it: the audit rows the approval wrote cannot be deleted
(`private.audit_log_immutable_guard`) and `invoice_three_way_approval_snapshots` still references
the approved invoice.

    update public.invoices set deleted_at = now()

                  'f4000000-0000-4000-8000-0000000000a2');
