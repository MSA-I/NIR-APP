THE ORACLE WAS CORRECTED ONCE, BEFORE THIS RUN, AND BOTH SIDES WERE RE-RUN AGAINST THE CORRECTED
VERSION. Said plainly because a red recorded against a different assertion is not this finding's
red. Two things were changed and nothing else:

  1. The harness stopped aborting on the first false case. As written it raised inside the first
     assertion, which made it impossible to show a control passing beside the failure -- and
     "everything failed" is indistinguishable from a broken harness. Every case is now recorded as
     an expected/observed pair, the whole table is printed, and one verdict at the end raises with
     the mismatches. The `live/direct.*` surfaces were added in the same change: they execute the
     leak itself rather than only asking the catalogue about it.
  2. The two configuration expectations were wrong. An organization is born with a default set of
     flag and autonomy rows -- the `zzz_organizations_prelaunch_assistant` and
     `zzz_organizations_prelaunch_autonomy` triggers write them on insert -- so the owner's
     literal was short by two flags and four policies. Measured, then written into the literal
     rather than filtered out: a filter that hid the defaults would leave the suite unable to
     notice a default row reaching an accountant.

  An earlier run of the uncorrected version of case 20/21 is not reported as this finding's red.
  The corrected version was run against head 0315 (this file) and head 0319 (the GREEN file).

  Every assertion is per row: surfaces are aggregated as `name=value` ordered by name and compared
  to a literal, never counted. The two rows that matter most are not catalogue questions -- they
  are the read itself, executed as that person:

    accountant / live/direct.profiles.phone
        expected: refused (42501)

  That is the finding, printed: an office clerk and an accountant listing a colleague's telephone
  number straight off `profiles`, with `set local role authenticated` and that person's own JWT
  subject in the path, so RLS, auth_org() and auth_role() are all really running. `-` is the value
  the fixture put there for the accountant, who has none; it is not an empty read.

  The same two actors also read `organizations.trial_ends_at`, all three feature-flag rows and all
  five autonomy-policy rows of their tenant. The four columns are readable by `anon` too.

  Every read here is on the guarded path. A read as postgres would prove nothing: postgres owns
  these tables and is exempt from the very policies under test.
