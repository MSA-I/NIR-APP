WHY THIS ORACLE EXISTS SEPARATELY FROM p111. The suite proves the SERVER now assigns
`invoice_date_missing` where only the date is unreadable. It cannot prove what the person is then
told: the sentence is chosen in the client, by `FILING_REASON_KEYS`, and one code with one
sentence is exactly the defect. Both halves are needed, so both are measured.

HOW THE RED WAS PRODUCED. The behavioural lines were reverted to the unfixed tree by
`.tmp/clientred.mjs revert`, and restored by `... restore` — a script that REFUSES unless its
anchor occurs exactly once in the file, so a silent double-edit is impossible, and that guard
fired for real on the first attempt (the sources are CRLF and the anchors were written LF; it
refused rather than half-editing, and the script was made line-ending aware). What was reverted:

  * `src/components/document-review/model.ts` — the two new `FILING_REASON_KEYS` entries.
  * `src/lib/i18n/dictionaries/he.ts` and `en.ts` — the two new sentences, and the reworded
    `filing_invoice_identity_missing` put back to its original "number OR date" form.
  * `supabase/migrations/0324_...sql` — moved out of the directory entirely, because this spec
    SCANS the migrations for every `v_reason_code := '<code>'` the ladder can assign and checks
    the client map against it in BOTH directions. Leaving 0324 in place would have produced a red
    for the opposite reason (a SQL code with no client sentence) and proved the wrong thing.

THE CONTROLS ARE THE ELEVEN TESTS THAT PASS IN THE SAME RUN, and they are the file's own
pre-existing ones — 0324 touches none of them. Two matter most:
  * `labels every code the SQL can assign` and `has no label for a code the ladder cannot
    produce` — the bidirectional scan of the migration SQL against the client map. Green in the
    red run (reverted tree, 0324 held out) and green in the green run (0324 present, map extended),
    which is the only pair of states in which both directions can hold.
  * `never prints a bare enum, even for an arm nobody labelled` — the fallback that made the red
    legible rather than a crash.

WHY THE MIGRATION SPELLS THE ASSIGNMENTS OUT IN FULL. `readLadderCodes()` matches
`v_reason_code := '<code>'` in the migration text. An anchored replacement normally builds its
replacement as a quoted plpgsql string, where every literal quote is doubled — and
`v_reason_code := ''invoice_number_missing''` does not match that pattern, so the two new codes
would have been invisible to the scan and the reverse check would have failed on the client map.
0324 therefore writes those arms inside DOLLAR-QUOTED strings, so the migration file literally
contains the assignment the database will run. That is the file telling the truth about itself,
not a guard being worked around.
