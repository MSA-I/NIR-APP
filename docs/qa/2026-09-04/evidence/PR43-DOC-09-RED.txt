  PostgREST maps SQLSTATE 55000 (raise_exception, class 55) to HTTP 500 by default. Nothing on
  the client can turn that into a 4xx. The only fix is the `using errcode` on that line — either
  a SQLSTATE PostgREST maps to 4xx, or PostgREST's own `PT4xx` response-status form.

WHY THIS AGENT DID NOT WRITE IT
  1. It is a SECURITY DEFINER body. PR 43's brief says to STOP and report before writing SQL for
     one: definer bodies are patched by ANCHORED REPLACEMENT against the LIVE body, not by
     re-declaring from the creating migration, which silently reverts security properties.
  2. It needs a migration number, and PR 43 is forbidden from drawing one (numbers are taken
     under the coordinator's lock).
  3. The body is PINNED by prosrc hash in four places, and all four move with any edit:
       supabase/migrations/0172_approved_credit_note_intake.sql:157, :337, :383
       supabase/migrations/0182_qualified_product_creation_guards.sql:217
       supabase/migrations/0227_document_intake_carries_the_evidence_currency.sql:414, :586, :629
       supabase/migrations/0230_repin_document_automation_after_currency_intake.sql:9-18
     `npm run check:anchored-replacements` and `check:exemptions` guard this; the prosrc hash has
     a known CRLF trap between Windows and CI, so the LF value has to be computed statically and
     the extractor verified against a known-good hash first.
  4. PRs 7/14/15 of this campaign may hold this function.
