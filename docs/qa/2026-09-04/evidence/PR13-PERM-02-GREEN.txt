THE FOUR THINGS THIS HAD TO PROVE
-------------------------------------------------------------------------------------
1. THE ACCOUNTANT NO LONGER READS ROWS THEY ARE NOT THE SUBJECT OF.
   accountant_a / pw_owner_a   true -> false
   accountant_a / pw_office_a  true -> false
   accountant_b / pw_owner_b   true -> false   (the same rule, second tenant)
   Exactly the three lines that were red, and no others moved.

2. THE SUBJECT STILL READS THEIR OWN ROW.
   accountant_a / pw_accountant_a  expected true, read true.
   owner_b      / pw_owner_b       expected true, read true.
   Without this the fix would have been "nobody but the owner", which is a different policy.

3. THE AUDIT-SURFACE ROLE STILL READS WHAT IT MUST — the one a careless narrowing breaks.
   owner_a / pw_owner_a       true    owner_a / pw_accountant_a  true
   owner_a / pw_office_a      true    owner_a / identity_control_a true
   owner_a / financial_control_a true
   The owner is asserted on EVERY password row of its own tenant, not on a sample.

4. CROSS-TENANT READS NOTHING.
   accountant_a / pw_owner_b        false   owner_a / pw_owner_b        false
   owner_a      / identity_control_b false   owner_b / pw_owner_a        false
   owner_b      / identity_control_a false   accountant_b / pw_owner_a   false

AND THE SET THAT WAS TAKEN AWAY IS EXACTLY THE SET THAT WAS NAMED
-------------------------------------------------------------------------------------
The suite's closing block ran (it is after the verdict, and the run exited 0). It compares,
row by row, everything tenant A's owner can read against everything tenant A's accountant can
read — the two hold identical scopes, asserted at the top of the suite, so any difference
between them is a difference of ROLE. It then requires that the difference contain NOTHING
except password_changed rows whose subject is not the accountant. Collateral damage from a
conjunct that was supposed to name one action would have been raised by name. None was.

It also asserts the reverse direction: the accountant reads no tenant-A row the owner does
not. A "fix" that widened instead of narrowed would fail there.

A HYPOTHESIS THAT WAS TESTED AND REJECTED, RATHER THAN ASSUMED
-------------------------------------------------------------------------------------
An earlier demo:restore failed with GoTrue HTTP 500 "Database error finding users". The
obvious suspect was p116 itself: it inserts five rows into auth.users with only (id, email),
leaving confirmation_token and its neighbours NULL, and GoTrue's admin list is known to fail
on exactly that. That would have been a real residual — check-quality-gates.ps1 runs p116 and
then runs demo:restore.

It was measured instead of assumed. p116 was run on a fully restored stack, leaving its five
fixture users present (5 of 5 with confirmation_token NULL, confirmed by query), and
demo:restore was run again: it succeeded, with all three sign-ins and all three profiles
proved. p116 does NOT break GoTrue.

The real cause was contention: at the moment of that failure the database had 0 migrations,
0 users and a postmaster one minute old, because another campaign
(docs/ux-remediation-documents-assistant), which does not read .claude/locks/supabase, had
begun rebuilding the shared stack underneath this run. Its reset finished at 12:12:21 local
and left the head at 0310-0314 + 0316/0317/0318 with 0315 gone — the same clobber the lock
file already records once. The stack was then re-taken from this worktree, the head re-read,
and the restore re-run and proved. No red or green above was measured during that window:
each was run against a head read out of schema_migrations immediately beforehand, and 0323
exists in no other campaign's tree.
