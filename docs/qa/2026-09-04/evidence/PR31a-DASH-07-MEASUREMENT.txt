PR 31a — DASH-07: why every cost column on /reports/products is empty.
=======================================================================================
MEASURE-FIRST PR. The ledger row said the root cause was not established by the sweep and that a
database check was needed before any oracle could be written. This file is that check: the actual
queries, the actual row counts, and the verdict they force. Everything below was run READ-ONLY
against the LIVE PRODUCTION project rkftlbctohswhbbiaqin through scripts/db-query.ps1
(-AllowProduction), on 2026-09-05. No local stack was touched and no lock was taken; the campaign
lock file states that remote read-only queries need no grant.

The window throughout is the sweep's own: 2026-01-01 .. 2026-09-04.

---------------------------------------------------------------------------------------
0. WHAT THE SWEEP RECORDED, AND ITS TWO HYPOTHESES
---------------------------------------------------------------------------------------
docs/qa/2026-09-04/dashboard.json entry 6:

  title  : "The product purchase summary produces no cost at all -- הוצאה, מחיר יחידה ממוצע and
            חויב are empty for all 115 products over nine months, with no message saying why"
  actual : "Root cause is not determinable from the UI -- either no invoice line in this tenant
            references a product, or unmapped_invoice_lines is failing to count lines it should;
            both need a DB look."

BOTH HYPOTHESES ARE WRONG, and the headline is false. Measured below.

---------------------------------------------------------------------------------------
1. THE READ PATH, READ FROM THE LIVE DATABASE RATHER THAN FROM A MIGRATION
---------------------------------------------------------------------------------------
  select pg_get_functiondef(
    'private.product_purchase_summary(uuid,date,date,uuid)'::regprocedure);

The wrapper the client calls is get_product_purchase_summary(date,date,uuid); the body above is
what it delegates to. Three findings from the body itself:

  a. The BILLED half is computed in the `invoiced` CTE, whose innermost table is
     public.invoice_line_matches, joined to public.invoice_lines and public.invoices.
  b. gross_amount_by_currency, average_unit_price and invoiced_qty are ALL guarded by
     `case when row.invoice_count > 0 then ... end`, so with no matched line the function emits
     NULL and never a fabricated 0. The em dashes on screen are the function behaving correctly.
  c. `unmapped_invoice_lines` is computed in the `unmapped` CTE, which reads public.invoice_lines
     DIRECTLY -- the SAME table the empty columns depend on.

(c) is the structural point of this whole finding and is returned to in section 5.

5. THE VERDICT, AND WHY IT IS STILL A DEFECT
---------------------------------------------------------------------------------------
DASH-07 IS A DATA DISPOSITION, NOT A CODE DEFECT IN THE REPORT. The server is right: an unknown
spend is NULL, and NULL renders as an em dash rather than a zero, which is the constitution's own
rule. Neither of the sweep's hypotheses holds -- it is not that lines exist and fail to reference a
product, and unmapped_invoice_lines is not miscounting: it is correctly reporting 0 because it
counts rows of the same empty table.

SO THE DEFECT IS THE DISPLAY, and it has a sharper shape than "no message". THE ONE IDIOM THIS
SCREEN HAS FOR EXPLAINING AN EMPTY MONEY COLUMN CANNOT FIRE IN THIS STATE. The unmapped-lines note
is guarded by `unmapped_invoice_lines > 0`, and that count reads public.invoice_lines -- the same
table whose emptiness empties the columns. No invoice lines means no unmapped invoice lines. The
note can therefore appear only when SOME lines exist and are unmatched, and is structurally silent
in precisely the case that empties the column completely. The sweep's own `expected` pointed at
that idiom as the fix; measurement shows the idiom is the hole.

THE FIX IS THEREFORE THE SENTENCE, ON BOTH SURFACES, FROM ONE PREDICATE:
  * billedNothingInWindow(products, unmappedInvoiceLines) in src/lib/productPurchaseWorkbook.ts --
    true only when the window returned products, NO product carries an approved payable invoice
    line, and no unmatched line is waiting either. Both halves earn their place: one billed
    product makes the sentence false, and when unmatched lines DO exist the report's existing note
    is the right one to show.
  * the screen renders a role="status" note naming the three empty columns, saying the words
    "this is not zero -- it is a figure not yet known", naming עלות לפי ההזמנה as what the report
    DOES know, and stating the step that fills the rest.
  * the exported sheet states the same sentence on ROW 2, appended to the window assertion rather
    than replacing it, because row 2 is where a sheet says what it holds. The finding's evidence
    named the file as well as the screen.

NO MIGRATION AND NO SUITE NUMBER WERE NEEDED OR DRAWN. Every fact the predicate needs is already in
the RPC response.

NO QUERY WAS WIDENED. Nothing was relaxed to make money appear; the report shows exactly the rows
it showed before, with a sentence beside them.

7. RESIDUALS -- recorded, not silently fixed
---------------------------------------------------------------------------------------
R1. PRODUCTION HAS NEVER HELD A SINGLE INVOICE LINE, in any of its five organisations. That means
    the three-way match -- the feature this report's whole billed half exists to serve -- is
    entirely unexercised in production. Not this PR's to change, and not a code defect on the
    evidence gathered here, but the coordinator/owner should know it: no live screenshot, export or
    smoke of that half proves anything today.

R2. THE FINDING'S HEADLINE IS WRONG and the ledger row quotes it. "produces no cost at all" was
    true before migration 0301 and stopped being true when 0301 and the עלות לפי ההזמנה column
    shipped -- both of which were live at sweep time (the frontend commit that adds the column is
    an ancestor of the merge the sweep names). The row is corrected rather than closed against the
    wrong sentence.

R3. THE TENANT-TEMPLATE EXPORT PATH IS UNTOUCHED. When an organisation has configured its own
    report template, renderConfiguredReportTemplate wins and the built-in builder never runs, so
    the row-2 sentence is absent from that file. Adding it means changing the template value
    contract in src/lib/reportTemplateExport.ts and the templates tenants already hold. Left alone
    deliberately; stated rather than discovered later.

R4. THE PER-ROW MIXED CASE IS UNCHANGED. When SOME products are billed and others are not, the
    unbilled rows still show three em dashes with no per-row explanation. That is the correct
    absence marker beside a populated neighbour, and a row-level caveat there would be noise; the
    finding measured the all-empty case and that is the case addressed.

R5. THE DEPLOYED BUILD IGNORES ?from=/?to= ON THIS SCREEN -- that is DASH-08, fixed elsewhere in
    this campaign and not yet released. The BEFORE run therefore typed the window into the two
    date inputs, exactly as the sweep's own repro says to, and the header was read back to prove
    which window the BEFORE figures belong to (115 מוצרים · 2026-01-01 עד 2026-09-04). The first
    BEFORE attempt, navigated by URL, silently landed on 20 products · 2026-09-01 עד 2026-09-05 and
    was discarded.
