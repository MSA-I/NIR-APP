1.3 READING THE PLAN — the four questions the row asks
-------------------------------------------------------
IS THE INDEX USED?  YES. `Index Scan using audit_logs_org_idx`, Index Cond `org_id = auth_org()`.
  The read is not a sequential scan and never was in any sample taken here.

WHICH PREDICATE IS NOT SERVED BY AN INDEX?  `action = 'password_changed'`. It appears under
  `Filter:`, not under `Index Cond:`, because no index on this table leads with or includes
  `action` for this value. The read therefore walks all 26,508 index entries for the tenant and
  discards 26,506 of them.

WHY THAT IS NOT AS BAD AS IT LOOKS, AND WHY THE ROW'S HINT ABOUT THE EXISTING INDEX RESOLVES.
  `text = text` is leakproof, so PostgreSQL assigns the client's filter security_level 0 and is
  free to order it by cost. It sits FIRST in the Filter list, ahead of `auth_role()`,
  `auth_scopes()` and the EXISTS. So the three SECURITY DEFINER functions and SubPlan 2 are
  evaluated only for the 2 rows that survive — SubPlan 2 reads `(never executed)`. 26,508 rows are
  rejected at roughly 2.5 microseconds each. That is why 26k discarded rows cost 67 ms and not 8 s.

  The index the row said already exists for the cross-scope path is `audit_logs_cross_scope_idx`,
  and it is healthy — it just is not reachable from this query. Its predicate,

1.6 PERM-03 — CONCLUSION AND THE FIX THAT IS DELIBERATELY NOT MADE
-------------------------------------------------------------------
No index is added. No predicate is rewritten. The plan is the proof, per the row's own instruction.

The option was costed and rejected on the measurement, not on effort. An index on
`(org_id, action, created_at DESC)` would turn the 26,508-row walk into a 2-row lookup and take the
read from 67 ms to under a millisecond. It would not have prevented a single one of the observed
500s, because the observed 500s are an 8 s wall that ten shapes hit, one of which does no table
work at all. Adding an index to a query that is already 67 ms, in response to a failure it did not
cause, is precisely the unmeasured change this campaign exists to stop — and it would leave the
real cause in place, where it will produce the same HTTP 500 on the next screen someone looks at.

TWO RESIDUALS, RECORDED RATHER THAN SILENTLY FIXED. Neither is claimed as PERM-03's defect and
neither is closed here; both want a DEBT section number, which this PR was not given.

  R1 — INSTANCE-WIDE STALLS. Ten query shapes with sub-50 ms minimums have been cancelled at the
       8 s `authenticated` ceiling, `check_plan_request()` among them at 7,473.5 ms on a 0.39 ms
       mean. Every REST call in the product passes through that hook, so while it stalls the whole
       API returns HTTP 500. This is the same class of event as ASSIST-11 in this sweep
       (`management_dashboard_snapshot` intermittently times out) and as the previously recorded
       502 on `my_subscription`. It is a capacity/observability item on a micro-class instance,
       not a defect in any one query, and it is the actual cause of PERM-03 as filed.

  R2 — THE AUDIT READ SCALES WITH TENANT HISTORY. Any filter on `action` walks the tenant's whole
       audit history behind the leakproof comparison: today 26,508 rows and 2,318 buffers for a
       2-row answer, and it grows linearly. It is cheap now and will not stay cheap. Related, and
       already filed: OWN-11 (the ledger is hard-capped at 400 rows with no paging). If a future
       screen filters this view by `action` over a larger tenant, the composite index above is the
       answer — proposed then, on a measurement taken then.

2.2 CAN ONE MUTATION WRITE TWO ROWS? NO — the live trigger, read from the database
-----------------------------------------------------------------------------------
pg_trigger on auth.users, user triggers only: COUNT = 1, name = audit_password_change.
pg_get_triggerdef:

    CREATE TRIGGER audit_password_change AFTER UPDATE ON auth.users
    FOR EACH ROW
    WHEN (((old.encrypted_password)::text IS DISTINCT FROM (new.encrypted_password)::text))
    EXECUTE FUNCTION private.audit_auth_password_change()

FOR EACH ROW, one row affected per GoTrue update, one INSERT in the function body (no loop, no
second insert path). There is no second trigger on the table that could file a duplicate. So two
rows require two UPDATE statements in which `encrypted_password` genuinely differed.

supabase/tests/p4_flags_identity.sql section (g), lines 1014-1070, asserts exactly that and asserts
the two ways it could have been wrong — per row, never by a table-wide count:
  :1026-1038  one UPDATE of encrypted_password  -> `count(*) = 1` for that entity_id, with org_id,
              user_id, entity_type and a non-null reason all pinned in the same predicate.
  :1050-1058  an UPDATE of last_sign_in_at       -> still `count(*) = 1`
              ("a sign-in was recorded as a password change")

2.3 THE TIE-BACK — two Auth requests, recorded before the sweep ever ran
-------------------------------------------------------------------------
docs/ROLLOUT-0291-0314-20260904.md, section 5 "הראיות", line 123-124, written by the rollout that
applied 0293 on 2026-09-03:

    ["Password change + 0293: `password_changed` rows 0 -> 1 after a real change -> 2 after the
      restore. The original password was restored AND verified by an actual sign-in."]

Two mutations, counted one at a time as they happened: the rollout set the owner's password to
prove 0293's trigger fires, then restored the original and proved the restore by signing in with
it. Two Auth requests. Two rows. 1.439 s apart is the interval between a set and its restore, which
is what that line describes.

Corroboration from the auth schema itself: `auth.users` for the owner shows
recovery_sent_at = 2026-09-03 22:19:34.777262+00 — 37 minutes AFTER these rows, so no recovery flow
is involved in them; and GoTrue's own user UPDATE statement
(`UPDATE "users" AS users SET ... "encrypted_password" = $6 ...`) stands at calls=11 / rows=11 in
pg_stat_statements across the whole retention window, i.e. GoTrue writes this table rarely and
individually.

VERDICT: CORRECT BEHAVIOUR. Each row ties back to one Auth request. PERM-05 is not a defect and no
trigger change is proposed. This is the outcome the ledger row and plan section A6 both anticipated.


2.4 THE ONE THING THAT DID NOT HOLD UP, and the residual it leaves
--------------------------------------------------------------------
Migration 0293's own header rejects `auth.audit_log_entries` as a reconciliation source because it
records a password change as `user_modified` with no field naming which attribute changed. That
reasoning stands, and production adds a harder fact to it:

    select count(*) from auth.audit_log_entries                       -> 0
    select count(*) ... where payload->>'action' = 'user_modified'    -> 0
    min/max created_at                                                -> null

The table is EMPTY in production. There is no GoTrue-side event log to tie to at all.

  R3 — A `password_changed` ROW CARRIES NO TIE-BACK HANDLE. Both rows have correlation_id = null,
       causation_id = null, old_values = null and new_values = null, and `auth.audit_log_entries`
       is empty. The columns exist on the view (`correlation_id`, `causation_id` are selected by
       `audit_log_read_model`) and indexes exist for them
       (audit_logs_correlation_idx, audit_logs_causation_idx — both at scans=0), so the surface is
       there and unused for this row class. Today the ONLY thing that can answer "which Auth
       request wrote this row" is a prose line in a rollout document. That was sufficient here
       because the rollout wrote one down; the next time two rows appear 1.4 s apart, whoever asks
       will have nothing inside the product to answer with, and will file PERM-05 again.

       This is NOT PERM-05's defect and is deliberately not fixed here: 0293 states in its own
       header that the trigger cannot see who made the HTTP call, and giving the row a request
       identifier is a design question about what GoTrue can be made to pass into its transaction —
       an owner-level decision with a migration behind it, not a diagnosis. Recorded for the
       coordinator; it wants a DEBT section number this PR does not hold.
