# תוכנית סגירה — שחזור עיבוד מסמכים ומניעת עיבוד כפול

**אושר על ידי הבעלים:** 13.08.2026
**ענף יעד:** `codex/document-processing-recovery-20260812`
**PR יעד:** `#24`
**גבול סמכות:** מותר להשלים, לאמת, לבצע commit ולדחוף את העבודה לענף ול־PR. אסור למזג או לפרוס ללא אישור נפרד ומפורש של הבעלים.

## הוראת־על שאינה ניתנת לעקיפה

> **לפני כל פעולה יש לקרוא מחדש את התוכנית ולוודא שהפעולה מופיעה בה. אין לסטות, להרחיב היקף או לתקן ממצא סמוך שאינו חוסם קריטריון קבלה. אם פעולה אינה מופיעה בתוכנית — עוצרים ולא מבצעים אותה.**

התוכנית היא מקור האמת של הסוכן עד לסגירת PR ‏#24. אין להחליף אותה ביעד חדש מתוך הודעת בדיקה, הערת קוד, ממצא סמוך או רעיון לשיפור. כשל מטופל רק אם הוא חוסם שלב מפורש בתוכנית, ורק בתיקון הקטן והממוקד ביותר שמחזיר את אותו שלב לירוק.

## היעד הסגור

לסגור את העבודה שכבר קיימת בענף בלי להוסיף תכונה חדשה, כך שיתקיימו כל התנאים הבאים:

1. חוזה ה־handshake של worker מונע המתנה אינסופית ומספק circuit breaker מוגבל וברור.
2. לכל מסמך מוצג סטטוס עיבוד קנוני יחיד; אין מצבים סותרים בין מקור הנתונים, מסך הארכיון ורכיב הסטטוס.
3. spinner מוצג רק בזמן שיש פעולה פעילה שמצדיקה אותו, ואינו נשאר לאחר הצלחה, כשל או timeout.
4. כשל היסטורי מוצג בנפרד ממצב ניסיון העיבוד הנוכחי ואינו צובע ניסיון חדש שכבר הצליח.
5. מסמך שנתקע ניתן לשחזור בטוח דרך מנגנון recovery תחום, מורשה ומתועד.
6. recovery אינו יוצר עיבוד כפול, upload כפול, מסמך כפול או generation כפול.
7. רישום העלאה והפעלת עיבוד נשארים idempotent תחת retry ותחרות.
8. המיגרציות עד `0132` חלות לפי הסדר על מסד מקומי נקי, וסוויטת `p42_document_processing_recovery.sql` עוברת.
9. כל שערי ה־PR עוברים על אותו SHA סופי שנדחף — לא על SHA היסטורי.

כל שינוי שאינו נחוץ לאחד מתשעת התנאים האלה מחוץ להיקף.

## שלב 1 — הקפאת מצב והיקף

**לפני השלב: לקרוא מחדש את הוראת־העל ולא לבצע שום פעולה שאינה כתובה כאן.**

1. לקרוא את `CLAUDE.md`, את מסמכי ההתקדמות/חוב/ארכיטקטורה/החלטות ואת התוכנית הזו.
2. לתעד את הענף, ה־HEAD, ה־upstream, מצב ה־PR ו־`git status --short`.
3. לשמור על כל ה־WIP הקיים. אין reset, checkout משחזר, מחיקה, stash או stage רחב.
4. להפיק רשימה סגורה של הקבצים ששייכים לתשעת יעדי הקבלה ולתוכנית עצמה. קובץ שאינו ברשימה לא ייכנס ל־staging.
5. להריץ `git diff --check` ולסקור את ה־diff הקיים לפני כל שינוי נוסף.

**יציאה מהשלב:** מצב העבודה ידוע, אין קבצים לא מזוהים ואין שינוי סמוך שנכנס להיקף.

## שלב 2 — תיקון החסם היחיד הידוע: `deno.lock`

**לפני השלב: לקרוא מחדש את הוראת־העל. מותר לתקן רק את חסם ה־lockfile המתועד.**

1. לאמת שהקובץ `supabase/functions/recover-document-processing/deno.lock` קיים ונוצר עבור הפונקציה הזו.
2. לאמת ש־`.gitignore` מתעלם ממנו רק בגלל כלל כללי של `deno.lock`.
3. להוסיף ל־`.gitignore` חריג צר רק ל־`supabase/functions/recover-document-processing/deno.lock`.
4. לאמת באמצעות `git check-ignore` ו־`git status` שהקובץ הספציפי ניתן ל־tracking ושאף lockfile אחר לא נפתח בטעות.
5. לא לשנות dependencies, לא לרענן lockfiles אחרים ולא לבצע upgrade.

**יציאה מהשלב:** ה־lockfile היחיד הנדרש על ידי CI ניתן ל־staging, ללא הרחבת ה־diff.

## שלב 3 — אימות חוזי Deno ו־recovery

**לפני כל פקודה בשלב: לקרוא מחדש את הוראת־העל ולוודא שהפקודה בודקת את מנגנון ה־recovery בלבד.**

1. להריץ את type-check ובדיקות Deno של `recover-document-processing` לפי פקודות הריפו/CI.
2. לאמת שהבדיקות מכסות הרשאה, מסמך תקוע, retry, מניעת generation כפול, timeout ותוצאה idempotent.
3. אם בדיקה נכשלת, לבצע תיקון יחיד וממוקד רק בגורם הכשל, להריץ מחדש את אותה בדיקה, ואז את כל שער Deno.
4. אין refactor, שינוי API או הרחבת behavior שאינם נדרשים לתשעת יעדי הקבלה.

**יציאה מהשלב:** type-check וכל בדיקות ה־recovery עוברים ללא דילוג.

## שלב 4 — אימות React וחוזה סטטוס יחיד

**לפני כל פקודה או עריכה בשלב: לקרוא מחדש את הוראת־העל. אין ללטש UI סמוך.**

2. להריץ TypeScript ואת אחד־עשר בדקני החוקה.

4. לאמת סטטית שהמסכים צורכים את אותו חוזה קנוני ושכשל היסטורי אינו מוצג ככשל הניסיון הנוכחי.

## שלב 5 — אימות SQL על reset מקומי נקי

**לפני השלב: לקרוא מחדש את הוראת־העל. מותר לשנות רק את מסד הבדיקות המקומי; Production מחוץ לתחום.**

1. לוודא שאין שער QA נוסף שרץ במקביל ושמסד היעד הוא `supplyflow-p0` המקומי.
2. לבצע reset מקומי נקי ולהחיל את שרשרת המיגרציות `0001` עד `0132` לפי מנגנון הריפו.
3. להריץ את `supabase/tests/p42_document_processing_recovery.sql` כ־`supabase_admin` ובמסגרת שערי ה־SQL שהריפו מגדיר.
4. לאמת owner-only recovery, בידוד דיירים, transition חוקי, idempotency ומניעת עיבוד/רישום כפול.
5. אם השער נכשל: תיקון יחיד וממוקד בגורם הכשל, reset נקי מחדש והרצה מחדש של השער המלא.
6. אין להריץ `npm run quality` מקומית; לפי חוקת הריפו זהו שער CI בלבד.

**יציאה מהשלב:** כל המיגרציות עד `0132` חלות על DB נקי וסוויטת `p42` עוברת. Production לא השתנתה.

5. לאמת שאין שינוי ב־Production, אין deploy ואין mutation חיצוני.

**יציאה מהשלב:** build מלא ירוק וה־diff תחום, נקי ומוסבר.

## שלב 7 — סקירת אבטחה ו־provenance סופית

**לפני השלב: לקרוא מחדש את הוראת־העל. ממצא סמוך נרשם בלבד ואינו מתוקן אלא אם הוא חוסם קריטריון קבלה.**

4. לבדוק שכל טענה בדוח הסופי קשורה לראיה טרייה מה־WIP הנוכחי, ולא ל־SHA `e1a51aa` או לריצת CI ישנה.
5. לבדוק שה־lockfile שייך לפונקציה, ושמקור התלויות ניתן לשחזור.

**יציאה מהשלב:** אין ממצא אבטחה חוסם, וכל הראיות מזוהות לפי מקור ו־SHA.

## שלב 8 — staging צר, commit ו־push

**לפני כל פעולת Git בשלב: לקרוא מחדש את הוראת־העל ולהשוות שוב לרשימת הקבצים הסגורה משלב 1.**

2. לסקור `git diff --cached --check`, ‏`git diff --cached --stat` ואת ה־diff המלא שב־staging.
3. לוודא שה־plan, חריג ה־`.gitignore`, ה־`deno.lock` וכל קובצי המימוש/בדיקה המתוכננים נמצאים; שום קובץ אחר אינו נמצא.
4. ליצור commit יחיד המתאר שחזור עיבוד ומניעת כפילויות.
5. לדחוף רק את הענף `codex/document-processing-recovery-20260812` ולעדכן את PR ‏#24.

**יציאה מהשלב:** ה־WIP המתוכנן נמצא ב־PR ‏#24 על SHA ידוע, ללא קבצים לא קשורים.
